Orientation

How to think about Agent 4

Agent 4 is a guarded deployment state machine. It does not decide whether a release is globally acceptable. It executes an already authorized, precisely typed change and refuses to claim success until an independent verifier confirms the result.

The simplest mental model: Agent 4 turns a signed intent into one exact Kubernetes patch, proves that patch is safe enough to attempt, watches the rollout, and prepares an exact inverse if recovery is required.

Responsibility boundaries

✓ Agent 4 does

  • Validate typed, authorized deployment operations.
  • Inspect one exact namespaced Deployment.
  • Build bounded patches and exact rollback intent.
  • Persist state, idempotency, locks and audit evidence.
  • Observe rollout and coordinate recovery.

× Agent 4 does not

  • Replace Agent 3 security policy.
  • Replace Agent 5 optimization decisions.
  • Invent HITL approval or an authorization issuer.
  • Fabricate Agent 1 success evidence.
  • Expose arbitrary Kubernetes or shell commands.

Safe execution

From request to verified result

  1. Validate the request. Pydantic rejects unknown fields, stale timestamps, mutable deployment tags, ambiguous targets and unsupported operation types.
  2. Verify authorization. The default verifier denies everything. A live path requires a trusted signed permit plus independently authenticated approval provenance.
  3. Create the journal record. Idempotency and the workload lock are acquired transactionally.
  4. Inspect the Deployment. Agent 4 reads the exact name and checks cluster identity, UID and resourceVersion.
  5. Run pre-flight. Allowlist, expected state, probes, resources, strategy, expiry and rollback completeness are evaluated.
  6. Build the patch. Only operation-specific paths are emitted, with server-enforced test operations for prior values.
  7. Dry-run the exact patch. Kubernetes admission sees the same generated patch with dryRun=All.
  8. Persist before mutation. The exact bytes and hash are durable before entering EXECUTING.
  9. Re-authorize immediately before mutation. Expiry, target, plan and patch binding are checked again.
  10. Apply once. The controlled adapter receives only a validated artifact and fresh permit.
  11. Observe rollout. Progress is bounded and distinguishes timeout, stall, failure, cancellation and identity drift.
  12. Ask Agent 1. Only trusted VERIFIED evidence can lead to SUCCEEDED.

State machine

RECEIVED → AUTHORIZED → PREFLIGHT_PASSED → PLANNED → DRY_RUN_PASSED
         → EXECUTING → OBSERVING → AWAITING_AGENT1 → SUCCEEDED
EXECUTING / OBSERVING / AWAITING_AGENT1
         → ROLLBACK_PENDING → ROLLING_BACK
         → ROLLBACK_AWAITING_AGENT1 → ROLLED_BACK
Uncertain mutation: a timeout does not mean “nothing happened.” Agent 4 re-reads the Deployment and reconciles exact fields. It never blindly retries a mutation.
Failed rollback verification: if the inverse conflicts, rollout fails, scope expires or Agent 1 cannot verify, the result is ROLLBACK_FAILED, not a false success.

Why the patch is constrained

  • Only image, replica and resource paths are generated.
  • JSON Pointer tokens are escaped correctly.
  • UID, resourceVersion, container name and prior field values are tested.
  • Secrets, cluster-scoped objects and unrelated containers cannot be targeted.
  • Callers cannot submit arbitrary JSON Patch through CLI or MCP.

The coordinator is powerful but dependency-controlled

The coordinator cannot contact a cluster on its own. It receives interfaces for authorization, inspection, dry-run, mutation, rollout observation, verification and persistence. Production safety therefore depends on both its logic and which adapters the private runtime chooses to inject.

Current assembly: the public runtime does not inject the live mutation adapter. A production-capable class existing in source code is not the same thing as a reachable production mutation endpoint.

Files: adapters & persistence

How Agent 4 reaches the outside world

agent1_verification.py

Defines the independent verification port. When no trusted implementation exists, it returns UNAVAILABLE.

compatibility.py

Reads actual Agent 3 and Agent 5 schemas. Their outputs remain evidence/advice and never become authorization.

kubernetes.py

Uses the official client for exact Deployment inspection and dryRun=All. There is no silent context fallback.

kubernetes_mutation.py

Contains a disabled default and a tightly allowlisted controlled adapter. It is not wired into public interfaces.

signed_contracts.py

Checks Ed25519 signatures, issuer, audience, expiry, scope, replay and approval provenance.

outbox.py

Provides transport-neutral at-least-once dispatch with leases, bounded retries and acknowledgements.

SQLite execution journal

persistence/sqlite_journal.py is the durable safety backbone:

Idempotency

A key cannot be reused for a different plan.

Workload lock

Only one active execution may own a workload.

Optimistic state

Transitions reject stale record versions.

Artifacts

Patch content is immutable and hash checked.

Audit chain

Every event hashes the previous event.

Outbox

Events and state commit in one transaction.

Audit limitation: hash linking makes tampering detectable, but SQLite is not an independently administered audit service. Production needs protected storage, backups, access controls and external retention.

MCP surface

The default MCP server exposes only capability discovery, operation validation, plan preview and Agent 3/5 evidence checks. Operator assembly may add constrained inspection and authenticated, redacted journal reads.

Never exposed through MCP: deploy, execute, live apply, rollback execution, shell, kubectl, caller-provided trust keys, caller-provided kubeconfig or arbitrary patch input.

Runtime assembly

runtime.py reads one operator-owned absolute configuration path. External callers cannot inject keys, clients, allowlists or permits. It validates READ_ONLY and future configuration shapes but always reports live execution unavailable.

Disposable Kubernetes integration harness

The integration/kubernetes/ folder contains:

  • harness.py — strict opt-in and exact test-target configuration.
  • rbac.yaml — a namespaced test ServiceAccount/Role/RoleBinding limited to named Deployment get/patch.
  • README.md — prerequisites and cleanup responsibility.

The optional tests verify exact reads, dry-run non-persistence, stale version rejection, RBAC denial and bounded rollout observation. They must target a disposable cluster.

How to explore Agent 4 locally

1. Activate the isolated environment

.\.venv-agent4\Scripts\Activate.ps1
python --version

2. Run all tests

python -m pytest agent4_deployment_recovery\tests -v

3. Watch specific behavior

# Execution, Agent 1 verification and rollback
python -m pytest agent4_deployment_recovery\tests\test_phase3_coordinator.py -v

# Kubernetes safety checks and typed patches
python -m pytest agent4_deployment_recovery\tests\test_preflight.py -v
python -m pytest agent4_deployment_recovery\tests\test_patch_builder.py -v

# Signatures, expiry, forgery and replay protection
python -m pytest agent4_deployment_recovery\tests\test_phase4_signed_contracts.py -v

# Process crash and restart consistency
python -m pytest agent4_deployment_recovery\tests\test_phase5_crash_consistency.py -v

4. Validate other-agent fixtures

python -m agent4_deployment_recovery.cli validate-agent3 `
  agent4_deployment_recovery\tests\fixtures\agent3_release_assessment.json

python -m agent4_deployment_recovery.cli validate-agent5 `
  agent4_deployment_recovery\tests\fixtures\agent5_resource_recommendation.json

5. Discover the CLI and MCP server

python -m agent4_deployment_recovery.cli --help
python -m agent4_deployment_recovery.cli preflight --help
python -m agent4_deployment_recovery.mcp_server
Best current visualization: the verbose tests show success, denial, timeout, uncertain apply, restart, verification failure and rollback paths. CLI commands render contracts, plans, reasons and patches as formatted JSON.

Reality check

Executable, but not yet a deployment product

Implemented and runnable

  • Strict operation and integration contracts.
  • Planning, hashing and state transitions.
  • SQLite journal, locks, audit and outbox.
  • Kubernetes inspection and server dry-run.
  • Constrained controlled-mutation component.
  • Rollout observation and exact recovery logic.
  • Signed-contract validation and replay defense.
  • Read-only CLI/MCP and extensive tests.

Not yet integrated

  • No production Orchestrator authorization issuer.
  • No trusted external HITL provenance service.
  • No production Agent 1 verifier transport.
  • No Kafka or gRPC outbox transport.
  • No operator-reviewed live composition root.
  • No production cluster/RBAC/network validation.
  • No web dashboard or deployment timeline UI.
  • No canary, blue/green or weighted routing.

Safety invariants to remember

  1. Agent 3 evidence and Agent 5 recommendations never authorize mutation.
  2. The default authorization and mutation implementations deny live actions.
  3. The exact dry-run patch bytes must be the exact persisted execution bytes.
  4. UID, resourceVersion and prior field values protect against race conditions.
  5. SQLite constraints—not only process locks—enforce idempotency and workload exclusion.
  6. Rollout convergence never substitutes for independent Agent 1 verification.
  7. Unknown schemas, strategies, states or ambiguous responses fail closed.
  8. A timeout causes reconciliation, not a blind retry.
Bottom line: Agent 4 is not static documentation. It is an executable, heavily tested backend control plane with read-only operational interfaces. It is intentionally not yet exposed as a live deployment service or visual dashboard.
